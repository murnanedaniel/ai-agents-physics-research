# SUPER-POSTER

A conference poster is skimmed in one minute; a super-poster gives about three minutes of depth, with interaction wherever useful. Help a researcher understand a paper in about **three minutes**, reading top to bottom: the problem and its importance, the mechanism, the evidence versus competitors, what is genuinely new, and how to reproduce or test it. Use British spelling and no em dashes. Budget **under 15 minutes of agent time**.

## Procedure

1. Resolve the paper and version; obtain full text from arXiv HTML, the publisher or PDF extraction. Inspect relevant PDF pages when extraction loses tables, equations or captions. If only the abstract is accessible, show **Abstract only: full text unavailable** prominently on the page and in chat. Retain section headings with explicit unavailable notices rather than inventing evidence, a schematic or a chart.
2. Read for the problem, mechanism, novelty, comparison table, setup, scaling, limitations and reproducibility. Keep an **evidence ledger**: exact numeric text, units, uncertainty, metric direction, dataset, split, method/baseline, experimental setting, and Table/Fig/section with a verified anchor or PDF page link. Record claims and availability statements with their locations too. Distinguish paper statements, our reading and our proposed experiments.
3. Copy the super-poster skeleton in [template.html](template.html). Fill the `poster-data` JSON from the ledger; the template computes chart coordinates. Generate the static fallback table from that same JSON at authoring time, serialising all rows into HTML before saving. Do not maintain a second handwritten dataset. Mark mechanism SVG groups with `data-step` matching the three to five How it works steps. Remove unused rows. Its empty mechanism SVG must be populated with a faithful drawing. Follow the reading order and content contract below. Aim for about 2,400px total height at 1280px width, roughly three screens. Order content by importance within the fixed reading order. Build the chart from the ledger, never from memory. Prioritise the main comparison over isolated impressive numbers. Shorten prose before reducing legibility; do not omit required sections to meet the time budget. Say “not stated” or “not verified” where appropriate.
4. Check every number against the ledger, including chart labels, comparators, dataset sizes, metadata and derived ratios. Every reported number must be backed by linked Table/Fig/section provenance. In prose cards, use at most one end-of-sentence tag per sentence: class `src`, 11px, muted colour, superscript-style, no brackets. Retain all exact locations in the ledger. Tables and charts use one linked caption line such as “Source: Table 1”, never per-row tags; tag individual cells or plotted values only if they come from a different source. TL;DR and verdict have no tags; support everything there elsewhere on the page. Use exact source text, sign, units and uncertainty. Explicitly label computed or rounded values, cite all inputs and explain the calculation. Axis ticks are scale coordinates, not reported measurements: label units and cite the panel's source. Proposed tests should avoid invented numeric targets. Use verified HTML anchors or a working relative PDF link with `#page=N`; a DOI landing page alone is not result provenance.
5. Complete [CHECKLIST.md](CHECKLIST.md). When a screenshot helper or headless browser exists, rendering is mandatory: capture the **1280x720 first screen and a full-page image at 1280px width in BOTH Full and Poster modes**, open all images and fix problems before reporting. A 1280x2200 viewport alone is not a full-page capture if content extends beyond it. Specifically inspect crossing schematic lines, repeated chart/key numbers, per-row source tags, overlaps, clipped SVG text, unreadable labels and empty space; re-render after fixes. Use the helper's full-page option, Playwright `full_page=True`, or an equivalent complete capture. Load with no hash for Full (default), and `#poster` for Poster. Full should be about 2,400px tall with details open; Poster should fit within 1,080px at 1280px width. Also check a viewport below 900px and a JavaScript-disabled page with all content and the complete data table visible. If rendering tools are unavailable or cannot launch, explicitly report that visual rendering was not checked and why. Screenshot creation alone is not inspection. Report exactly what was checked. Screenshots cannot verify hover/click behaviour: try depth buttons, keyboard focus, chart filters/tooltips, step highlighting, Play/Stop, details and slider in a browser; disclose any interaction checks not performed.
6. Save the finished super-poster to `./posters/<short-name>.html` or the user's path. Report the path, up to three verified key numbers with their provenance, render-check status and remaining verification gaps. Disclose abstract-only access again. The HTML must render offline; following remote evidence links can require connectivity.

## Content and reading order

- **Title strip, TL;DR, verdict:** paper identity and source link; TL;DR exactly three sentences and at most 60 words total, in order problem, method, result. Immediately follow with one line beginning “Reader's verdict:” and labelled “agent's reading”, stating what is genuinely new and how convincing it is. Reader’s verdict is at most 30 words. Neither TL;DR nor verdict carries tags; support all their claims elsewhere on the page.
- **The problem | Mechanism schematic:** problem card has two to three sentences, a concrete physical example of the failure and a plain-language definition of the key jargon term. The schematic shows actual manipulated objects and relationships, such as atoms with local edges inside a dashed cutoff circle and global nodes, detector layers and tracks, or a sparse matrix. Use clean geometry, consistent spacing and at most about 10 primary objects. Put two to four short callouts in empty margins with thin leader lines. No arrows, labels or leaders may cross edges or each other. Distinguish local and global structure spatially, for example a local cluster on the left and virtual/global nodes in a row above or to the right. For dense connectivity, draw representative connections and state “each X connects to all Y”. Cite its basis and give an accessible description. It must occupy at least half the page width on wide screens. If the mechanism cannot be drawn faithfully, draw a simple labelled data structure. Never substitute a flowchart of words or three labelled boxes and arrows.
- **Main result chart (wide) | Key equation or scaling + key numbers:** inline SVG dot or bar chart from the main comparison table: the method versus two to five baselines, on one to three metrics as small multiples. Keep row order consistent; label metric, units and setting. Use one shared direction note (for example “lower is better”). If metric directions differ, disclose that explicitly in that note; never silently reverse a metric. Label values at the marks and use a shared source caption. Plot every metric in the main comparison where the method loses to a competitor, rather than only mentioning it in text. Prefer value-labelled paired dots over bars when two metrics share a panel; use separate panels for differing units/scales. Method is accent blue; baselines are grey-blue. Bars start at zero; dot plots may use a clearly labelled non-zero scale. Never mix incomparable settings or fabricate missing values. Directly below the chart, one sentence stating exactly what the evidence supports. If fewer baselines or metrics are available, show only verified comparisons and state the gap. The adjacent equation/scaling line uses HTML text with `<sub>`/`<sup>`, defines symbols, compares cost where supported and has provenance. The key-numbers slot carries the paper’s other main claim: never repeat a chart value as a key number. If the selling point is cost (time, memory, scaling) or another axis absent from the main chart, add a second small chart using the same scaffold, for example relative time and memory per method, rather than isolated big numbers. Keep at most two big numbers on the whole page, each with a named comparator, setting and provenance for both values. Remove the slot if no other supported claim exists.
- **How it works | Setup:** three to five one-line steps, as text rather than a box flowchart. Setup includes datasets and sizes, splits, model sizes and compute/hardware. Use “not stated” for each missing field; do not infer hardware or model size.
- **Where it sits:** full-width table of three to five prior/competing methods: method | approach in a few words | cost | how this paper compares. Use one shared source caption; tag only cells from a different source. State when cost is not stated or comparison is indirect. Include fewer rows only if the source cannot support more, with an explanation.
- **How strong is the evidence:** full-width evidence drawer of three to four main claims: claim | evidence (what was actually run) | strength. Each row is an open `<details>` element: its summary shows claim | strength, and its body shows what was actually run, verbatim supporting sentence(s) with a linked section, and what was not tested. Preserve qualifications in quotes; mark unavailable text honestly. Each rating is strong / moderate / weak followed by a four-word reason grounded in the evidence, for example “Matched settings across datasets”. Label the strength assessments as our reading. Judge support for the precise claim, not the paper's reputation. Include stated limitations with provenance; label limitations not stated by the paper “our reading”. A narrow controlled comparison can be strong for a narrow claim without proving generality.
- **Reproduce | If we wanted to test it:** final group of two compact cards. Reproduce includes code link and licence, data links and sizes, checkpoints yes/no (or not stated), rough compute and one gotcha if found; distinguish reported compute from a labelled estimate with sourced inputs. Do not infer a licence or checkpoint availability from a repository link. Proposals: two to three feasible experiments, each with an intervention/comparison and figure of merit, labelled “our proposals”. Inline glossary: wrap jargon in `<dfn tabindex="0" data-def="...">term</dfn>` for hover/focus definitions. Keep three to six one-line definitions of terms actually used in an open fallback `<details>` at the end; no separate glossary card.

## Visual and technical contract

Use two columns on wide screens, full-width tables, and two cards in the final group; collapse every group to one column **under 900px**, preserving DOM reading order. The mechanism occupies the wider first-row column; the chart occupies the wider results column. At 1280x720, show the title, all TL;DR and verdict, and at least the top of both problem and mechanism cards. Aim for about 2,400px at 1280px width, roughly three screens. Cut low-value text before shrinking type. Order content by importance within the fixed reading order. Avoid huge empty areas, fixed card heights and hidden overflow used to conceal content.

Body text is 15 to 16px, tables 14px, minimum 13px for content, including SVG labels after scaling. The sole exception is `.src` provenance tags: 11px, muted, superscript-style and bracket-free. Use compact bold accent card headings and generous but economical spacing. On narrow screens, reflow drawings or allow local horizontal scrolling at a readable SVG size rather than shrinking labels below the minimum.

Self-contained HTML with inline CSS and inline SVG for all graphics. Allow exactly one executable inline script using vanilla JS, plus one inert `<script type="application/json" id="poster-data">` data block. No libraries, network calls, eval, dynamic code, inline event-handler attributes, external assets, fonts, stylesheets, images, embeds, CSS imports or remote CSS URLs. Use system fonts. Preserve surface `#fcfcfb`, text `#1f1f1d`, muted `#6b6a64`, accent `#2a78d6`, baseline series `#9aa7b8`, grid `#e6e5e0`. Paper, code, licence, data and checkpoint navigation links are allowed; they must not trigger requests on page load. Verify destinations and disclose inaccessible links. Use the footer exactly: “Super-poster generated by an agent from <source>; every number links to its location in the paper; check before citing.” Link the source; the existing TL;DR/verdict and shared-caption provenance conventions still apply.

## Progressive enhancement and interactions

Everything is visible by default without JavaScript, including the static chart table, mechanism, text steps, evidence and secondary details (all authored `open`). Only inert enhancement controls start hidden. Add the body class enabling controls in JS; hide the fallback table only after a chart renders successfully. All actions use native buttons, selects or range inputs with labels, visible focus styles and keyboard access. Full is the default; `#poster` on load and hash changes selects Poster using a body class and CSS. Poster retains identity/navigation, TL;DR/verdict, mechanism, main comparison and the two distinct key numbers (or fewer if unsupported); other content is hidden. Never conceal abstract-only warnings.

- Depth buttons read “Poster (1 min)” and “Full (3 min)”, with `aria-pressed`. Setup, Where it sits, Reproduce and If we wanted to test it are `<details open>` in Full, hidden in Poster; preserve their state on mode switches.
- Stepper buttons derive their labels/captions from the three to five How it works steps. Use matching space-separated `data-step` numbers on SVG elements, dim only non-matching elements, and show one caption. Play cycles every 2.5 seconds; Stop and manual selection stop the timer. Show all restores the static view. The text steps remain visible without JS.
- Chart rows are `{method, system, metric, value, err, unit, source}`; `source` holds `label` and verified `href`. Preserve exact numeric strings, including trailing zeroes; use null for missing values/uncertainties. Supply `highlightMethod` and `metrics: [{name, direction}]` in the same JSON. Metric buttons and an All/individual system selector filter SVG dot plots. Default to all metrics so losses remain visible. Separate settings/units into panels, retain method order, label values, accent the paper's method, and include value ± err unit and source in hover/focus text. Unknown uncertainty must say so. Keep the shared linked caption. Filtering never changes the evidence takeaway. A second chart for an additional selling point uses the same rows/renderer and source rules, with unique controls/IDs if split into a separate container.
- For chart data the agent fills only JSON. Before delivery, mechanically generate and HTML-escape the static table from every JSON row, preserving exact values and uncertainty, directions, settings and shared provenance; link only cells with differing sources. Validate equality against JSON and ledger. This authoring-time step is mandatory because runtime JS cannot populate a JS-off fallback. Escape `<` as `\u003c` in JSON; never insert data with `innerHTML`.
- Retain the optional scaling card only for a paper-stated scaling claim. Fill the documented `scaling` JSON schema, named complexities, log-scale N bounds and reference N. Curves are cost divided by cost at reference N, with logarithmic axes; disclose normalisation and assumptions. Label “illustrative, from the stated complexity, not the paper's data”. Plot ledger measurements as sourced dots only when units/normalisation match; cite inputs and explain any computed normalisation. Keep measured values and sources in static text as well. Never fit coefficients or invent measurements. Extend the explicit function map for other stated complexities without eval.
- Keep all original evidence requirements, including loss cases, no duplicated chart/key numbers, geometry hygiene and exactly sourced claims. Interactive controls do not replace required content or justify hiding a weak result. Shorten prose to meet height targets; never drop baselines or losing metrics to fit.

## Serialise the chart fallback

After filling JSON, run this authoring-time recipe with the output HTML path as the argument (`python3 - path/to/poster.html <<'PY'` followed by the code and closing `PY`). It generates the table and shared caption; no additional script is shipped in the page. With no data, retain explicit unavailable notices instead. Inspect generated links as part of the provenance check.

```python
import html, json, re, sys
from pathlib import Path
path = Path(sys.argv[1])
page = path.read_text()
data = json.loads(re.search(r'<script type="application/json" id="poster-data">(.*?)</script>', page, re.S)[1])
esc = lambda value: html.escape(str(value), quote=True)
def replace(tag, ident, content):
    global page
    pattern = rf'(<{tag} id="{ident}">).*?(</{tag}>)'
    page, count = re.subn(pattern, lambda m: m[1] + content + m[2], page, flags=re.S)
    assert count == 1, ident
if data['rows']:
    shared = data['rows'][0]['source']
    rendered = []
    for row in data['rows']:
        cells = [esc(row[k]) if row[k] is not None else 'not reported'
                 for k in ('method', 'system', 'metric', 'value', 'err', 'unit')]
        if row['source'] != shared:
            source = row['source']
            cells[3] = f'<a href="{esc(source["href"])}" title="{esc(source["label"])}">{cells[3]}</a>'
        rendered.append('<tr>' + ''.join('<td>' + cell + '</td>' for cell in cells) + '</tr>')
    replace('tbody', 'chart-fallback-rows', ''.join(rendered))
    replace('caption', 'fallback-caption', esc(' · '.join(m['name'] + ': ' + m['direction'] for m in data['metrics'])))
    replace('figcaption', 'chart-source', f'Source: <a href="{esc(shared["href"])}">{esc(shared["label"])}</a>')
    path.write_text(page)
```
